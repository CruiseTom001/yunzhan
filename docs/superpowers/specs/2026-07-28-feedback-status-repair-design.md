# 反馈状态更新故障修复设计

## 目标

- 超管可将反馈更新为 `open`、`seen` 或 `resolved`。
- `seen_at` 或审计日志的附属写入失败时，不回滚已经成功的核心状态更新。
- 修复生产库中名称不一致的历史状态约束。

## 非目标

- 不改变反馈状态枚举、权限模型或前端入口。
- 不删除反馈、审计记录或用户数据。

## 根因与方案

现有接口把状态、查看时间和审计日志写入同一事务。任何附属写入失败都会让事务进入失败状态并回滚核心状态。数据库中还可能保留名称不是 `feedback_status_check` 的历史检查约束，旧迁移无法移除。

修复分两部分：

1. 先以独立 SQL 更新 `feedback.status`，成功后再尽力写入 `seen_at` 和审计日志；附属失败只记录安全摘要。
2. 追加迁移 `010_feedback_status_constraint_repair.sql`，仅移除 `feedback` 表中定义引用 `status` 的检查约束，规范旧值后恢复统一约束。

## 安全与兼容性

- 接口仍要求登录、超级管理员权限和状态枚举校验。
- 审计失败不会暴露数据库详情；日志只记录阶段和 PostgreSQL 错误码。
- 迁移不删除业务记录；未知旧状态规范为 `open`。
- 部署前按现有流程备份生产 PostgreSQL；回滚应用代码不影响新约束。

## 验证

- 单元测试覆盖核心状态成功、附属写入失败和记录不存在。
- 完整运行项目质量门禁。
- 上线后用生产超管账号分别验证“已查看”和“已处理”。
